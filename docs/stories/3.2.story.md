## Descricao

Atualmente, step executions são armazenadas como JSONB flat (`step_statuses: { stepId: 'completed' }`) sem granularidade. Não há notas, timestamps por step, nem registro de quem completou cada step.

Esta story enriquece o tracking de execução para capturar dados operacionais reais.

### Schema Atualizado

```sql
-- Alterar step_statuses de Record<string, string> para Record<string, StepExecution>
-- Na tabela workflow_executions, o campo step_statuses passa a ter esta estrutura:

/*
step_statuses JSONB exemplo:
{
  "kickoff": {
    "status": "completed",
    "started_at": "2026-03-11T10:00:00Z",
    "completed_at": "2026-03-11T10:45:00Z",
    "completed_by": "466187",
    "notes": "Reunião feita com cliente, definimos escopo inicial",
    "duration_seconds": 2700
  },
  "setup-clickup": {
    "status": "in_progress",
    "started_at": "2026-03-11T11:00:00Z",
    "completed_at": null,
    "completed_by": null,
    "notes": null,
    "duration_seconds": null
  }
}
*/
```

### TypeScript

```typescript
interface StepExecution {
  status: 'pending' | 'in_progress' | 'completed' | 'skipped' | 'failed'
  started_at: string | null
  completed_at: string | null
  completed_by: string | null
  notes: string | null
  duration_seconds: number | null
  failure_reason?: string | null
}
```

### Funcionalidades

1. **Schema migration** — Migrar step_statuses existentes para novo formato
2. **Step Notes Dialog** — Modal ao completar step para adicionar notas (opcional)
3. **Duration tracking** — Auto-calcular duração ao completar (completed_at - started_at)
4. **Failed state** — Novo status `failed` com campo `failure_reason`
5. **Retry logic** — Botão "Tentar novamente" que reseta step para `in_progress`
6. **Audit display** — Mostrar quem completou cada step e quando
7. **Step timeline** — Visualização de timestamps por step na execução
